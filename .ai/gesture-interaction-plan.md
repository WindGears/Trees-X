# 桌面手势控制与动作反馈方案

日期：2026-09-18，实施状态更新于 2026-09-19。有限惯性、入镜基线、统一部件/操作盘目标、默认试用悬停确认、可切换捏合、丢失冻结与输入所有权已实现，单元测试与合成轨迹浏览器检查已通过。真人验收仍待进行；速度光弧、边缘引导与完整成功微动效尚未实现。下文保留原设计背景与目标，不将其全部视为已交付。最新证据见 `heritage-integration.md`。本文更新 `gesture-research.md` 中旋转失踪后立即停下的旧建议，不撤销选择确认的防误触约束。

## 推荐方向

保留 MediaPipe 与现有 Worker，引入独立的连续运动层。体验分为“观察”和“选择”两个明确模式：观察采用相对掌心移动与有限惯性；选择采用吸附、目标捕获和明确确认。默认先试悬停确认，保留捏合确认作为可切换选项，二者不同时监听。默认选择策略须经过真人对照测试再最终锁定。

惯性降低漏检带来的视觉中断，不能提升关键点识别率，也不能作为确认动作的证据。目标是省力、可预期、有控制感，而不是长时间自动旋转。

## 当前链路与问题

- `useGestureSession.ts` 目前最多每秒提交 15 帧，仅一帧在途；实际有效频率还受推理耗时影响。
- `useGestureInput.ts` 每次结果直接调用 `bridge.rotate(result.dx)`；`CameraController.vue` 随即改变相机方位。识别与运动更新耦合，是顿挫的潜在来源。
- `detector.ts` 的 `dx = 0` 同时代表静止、入镜尚未就绪、姿势不匹配和缺失，运动层无法区分“用户停手”和“暂时没看到手”。
- 任一空帧会清除旋转基线，并重新等待开掌就绪。固定的每样本位移死区也会使不同输入频率产生不同手感。
- 已有 One Euro、掌心中心、选择的 64/96 CSS px 边界、捏合捕获、校准与 250 ms 丢失宽限；应扩展现有机制，不再重复叠加强滤波。
- 现有手势选择只有一个当前热点，不具备整页按钮和全部部件的统一手势命中能力。
- 当前“商品旋转”实际由相机环绕实现。保持这一语义，避免同时旋转模型破坏部件聚焦和结构展开。

## 动作映射

| 场景                   | 用户动作                       | 系统响应                                               |
| ---------------------- | ------------------------------ | ------------------------------------------------------ |
| 开启                   | 点击开启手势，许可摄像头       | 默认进入观察，先显示取景与开掌提示                     |
| 观察                   | 张开手掌后左右移动             | 以掌心相对位移控制水平环绕；不要求手对准商品           |
| 停住                   | 可见的手停在原处               | 快速柔和制动，方便停在想看的角度                       |
| 离开画面或短暂漏检     | 不要求补做动作                 | 延续最后可信转速并逐渐衰减；无可信速度则保持静止       |
| 重新入镜               | 开掌短暂停留                   | 从新掌心位置建立基线，平滑接回，不补算离镜期间位移     |
| 选择                   | 显式切到选择模式，食指瞄准目标 | 相机停止惯性，显示吸附光标与候选目标                   |
| 悬停确认               | 在同一候选目标内停留           | 先就绪，再完成进度环，执行一次动作；离开后才能再次触发 |
| 捏合确认选项           | 瞄准后捏合，再明确松开         | 捕获目标，容忍收指移动；有效释放时执行一次             |
| 缩放、配色、结构、视角 | 选择有名称的大按钮             | 调用现有操作意图，保持和鼠标一致                       |
| 接管                   | 鼠标拖动、键盘或控制台操作     | 清除手势运动与待确认，立即执行用户的新意图             |

首轮只做水平环绕，保留滚轮和按钮缩放。俯仰仍由鼠标与命名视角提供。双手缩放、手掌前后推拉缩放、挥手切商品、五指展开触发结构均不进入首轮，避免增加姿势识别和动作冲突。

模式入口固定可见，用鼠标或键盘切换。第二步扩展选择目标后，“返回观察”也可直接选择；观察切到选择仍保留显式入口。第一版不宣称从开启到全部操作都能脱离鼠标。若后续确需全程免触摸，再单独验证常驻模式按钮的停留触发和旋转抑制区。

## 连续运动与惯性

流程：采样与关键点 → 有效性/姿态/时间检查 → 相对运动意图 → 独立运动状态 → GSAP ticker → 现有相机控制器。

1. 信号携带采样时间、接收时间、输入代次及状态；至少区分 `arming`、`moving`、`still`、`pose-released`、`missing`、`stale`。不能用一个零位移代替全部状态，也不能把模型阈值显示成实时“识别置信度”。
2. 用相邻有效样本的真实时间差估计角速度，死区按速度/时间定义。异常跳变、时间倒退、旧代次和过期结果不能注入动量；失踪后第一帧只建立基线。
3. 跟随时由渲染时钟连续更新角度；避免把一个样本位移逐帧重复相加。采用短响应时间，慢移能精调，正常横移能浏览。现有 One Euro 与运动响应共同调参，控制总延迟。
4. 新样本间隔内允许短暂延续可信速度；超出预期到达时间或收到明确缺失后开始衰减。使用单调时钟维护新鲜度，即使 Worker 完全不再返回结果也能停下。
5. 衰减采用时间一致的指数模型：`v1 = v0 × exp(-dt / τ)`，区间转角为 `v0 × τ × (1 - exp(-dt / τ))`。相同输入不应因显示器 60/120 Hz 产生不同惯性。
6. 可见静止使用更快制动；可见收手/姿势释放使用短制动，不把不满足开掌当作新的语义命令。缺失使用较缓的滑行，连续空帧不能刷新滑行寿命。
7. 重新入镜时保持已有角度，新基线就绪后用新速度平滑接回。没有稳定追踪身份时，掌心/尺度明显不连续按新手处理，不跨手继承位移。
8. 鼠标接管、模式切换、校准、关闭摄像头、隐藏页面、离屏、上下文丢失、模型切换与卸载都立即清除速度、输入缓存和时钟；恢复时重新就绪，不追赶后台时间。

以下是实验初值，属于本项目设计假设，不是来源的标准或已测结果：

| 参数                 | 起点                              | 目的                                               |
| -------------------- | --------------------------------- | -------------------------------------------------- |
| 首次/重新入镜就绪    | 约 120 ms，且至少两个有效样本     | 过滤单帧偶然命中，建立新基线                       |
| 运动跟随响应时间常数 | 约 70 ms                          | 平衡输入阶梯感与延迟                               |
| 可见静止制动时间常数 | 约 60 ms                          | 约 180 ms 内削减 95% 速度                          |
| 缺失滑行时间常数     | 约 320 ms                         | 温和衰减，避免出镜即停                             |
| 角速度上限           | 1.5 rad/s                         | 限制误识别和快速甩手的视觉幅度                     |
| 缺失后的滑行截止     | 速度低于 0.035 rad/s 或最多 1.2 s | 保证不会无限旋转                                   |
| 未收到新结果的宽限   | 根据近期输入间隔估计，上限 150 ms | 避免正常采样间隙误判丢失，限制 Worker 卡住后的续转 |

上述速度上限与衰减常数对应衰减阶段理论最大续转约 27.5°；结果等待宽限还会增加少量转角，不能把 27.5° 宣称为整个缺失过程的硬上限。验收需记录从最后一次有效采样开始的实际总续转角，并据真人手感收紧参数。进入长缺失后停止更新，不能不断重新启动 1.2 秒滑行。

## 选择与误触控制

悬停方案建议先试“稳定瞄准 150 ms + 确认 650 ms”。在候选目标内的小幅抖动不会重置，越过退出边界或切换候选则取消。确认后必须离开目标或明确重新武装，不能每过 800 ms 重复触发。配色、结构等动作也适用这一规则。

捏合沿用已有双阈值与校准：稳定瞄准 → 捕获目标 ID → 捏合进度 → 有效松开 → 确认。指尖移动不再参与捕获后的目标更换；明显掌心移开、超时或目标失效则取消。捏合尚未达到就绪条件时不要显示“已按下”。

缺失时两种确认都冻结，指针不外推，进度不再增长。短于 250 ms 可保留候选/捕获，但不计入有效停留或捏合持续时长；恢复后必须继续得到有效证据。松开发生在遮挡期间不能确认，超过宽限取消并要求重新就绪。惯性只适用于浏览运动。

后续新增目标注册表，统一承接可见部件热点和手势操作盘，保存稳定 ID、屏幕区域、可用性、动作与优先级。命中统一使用 CSS 像素，适配 Canvas 偏移和浏览器缩放；部件被遮挡、相机动画中或目标消失时撤销命中。多个吸附区重叠时保留当前候选，只有离开退出区后才切换，避免目标来回跳。

不直接让手势去命中目前紧密排列的小按钮。选择模式显示专用大目标，优先提供部件、放大/缩小、结构、配色和返回观察；分组展开，每屏控制数量。它们调用原按钮同一业务意图，不复制第二套状态。

## 反馈与动效

| 状态         | 局部反馈                                 | 初始节奏                           |
| ------------ | ---------------------------------------- | ---------------------------------- |
| 等待入镜     | 小取景预览、手掌轮廓与一句提示           | 保持可见，不循环闪烁               |
| 就绪         | 舞台下缘显示“观察 · 已连接”              | 约 120 ms 淡入                     |
| 正在旋转     | 光环的一段亮弧随转向/转速响应            | 与真实运动速度同步；不对整屏频闪   |
| 靠近取景边缘 | 预览边缘与简短方向提示                   | 稳定越界趋势后出现，避免逐帧开关   |
| 短暂漏检     | 保留舞台连续运动                         | 小于 120 ms 不急于改变文案         |
| 惯性滑行     | 显示“惯性滑行”，亮弧逐渐收弱             | 跟随实际减速                       |
| 已停且丢失   | “将手移回取景框”                         | 不使用红色报错或反复弹窗           |
| 目标候选     | 目标轻微放大、描边，光标软吸附           | 约 100 ms；不移动按钮布局          |
| 确认中       | 环形进度与目标名称；捕获后指针固定在目标 | 进度对应真实状态，不靠独立动画填满 |
| 确认成功     | 短促收束/勾选，随后镜头聚焦或状态变化    | 成功约 200 ms；镜头沿用约 0.8 s    |
| 取消         | 进度回落，目标恢复                       | 约 150 ms，不制造失败惩罚          |
| 鼠标接管     | “已切换鼠标 · 恢复手势”                  | 不因手仍在镜头里而自动抢回控制权   |

反馈靠近正在操作的目标。取景和详细诊断可折叠；骨架、毫秒数、阈值不占主视觉。声音仅作为以后可关闭的增强项，首轮无需增加。

减弱动态偏好下关闭惯性续转、装饰性速度光环与确认缩放，直接跟随有效输入，保留文字、描边和真实进度。镜头直接抵达目标，沿用项目规则。

## 所有权与架构

相机一次只有一个控制者。用户新意图先取消旧惯性/补间再执行；手势确认触发镜头时暂停运动，镜头完成后回到明确状态并要求重新建立输入基线。用户鼠标接管后需显式恢复手势，避免自动抢回。视角、聚焦、缩放、结构和导览复用已有请求，重播视觉演出不能恢复旧速度。

具体交接规则：手势确认启动的镜头记录其输入代次；完成时仅在代次仍有效、摄像头仍开启且没有新输入接管时返回选择模式，并清除候选与确认进度、重新武装。鼠标或键盘启动的镜头完成后保持鼠标控制。被打断的动画回调无权恢复旧控制者。

| 位置                                 | 职责                                                         |
| ------------------------------------ | ------------------------------------------------------------ |
| `lib/gesture/detector.ts`            | 保留关键点几何与滤波，输出有时间和原因的有效运动/选择意图    |
| 新 `lib/gesture/rotationMotion.ts`   | 纯状态机与角速度积分，负责跟随、制动、滑行、就绪与重置       |
| 新 `composables/useGestureMotion.ts` | 唯一持有运动实例与 GSAP ticker；处理活跃状态和清理           |
| `lib/gesture/bridge.ts`              | 分离提交运动样本和应用相机增量；提供停止原因、模式和反馈事件 |
| `useGestureInput.ts`                 | 协调输入、校准、选择，不再直接把识别频率当运动频率           |
| `CameraController.vue`               | 继续唯一应用环绕与镜头补间，避免并行修改模型 transform       |
| `useGestureSession.ts`               | 继续唯一持有视频和 Worker；所有失活路径清除运动与待确认      |
| `selection.ts` / 后续目标注册表      | 候选、捕获、有效停留、一次确认和取消；与惯性完全分开         |
| 手势面板 / 独立反馈组件              | 呈现模式、状态、操作盘和可折叠预览                           |

运动计算只需固定数量标量，已有单 Canvas/renderer 不变；按帧更新相机需要渲染时调用 invalidate。高频速度不进入 Pinia，业务状态仅在事件边界更新；逐帧不新建向量、数组或 tween。运动时钟只在需要跟随/滑行且展示区域活跃时运行。该结构以后可接鼠标拖动惯性或其他追踪器，无需更换场景体系。

## 实施与验收顺序

1. **连续旋转与失踪容错。** 区分样本状态，接入独立运动层、制动、重入镜与所有权，增加最小状态反馈。先保持现有选择逻辑，做一轮真人手感对比。
2. **确认动作可靠性。** 增加悬停方案和有效时间计数，保留捏合捕获；先在当前单热点验证，再扩展统一目标注册与大操作盘。
3. **统一动画语言。** 接入速度亮弧、边界提示、目标进度和成功反馈；完整检查缩放、聚焦、结构、导览、配色与重播的控制权。

每步通过后再扩展下一步，不把视觉增强和识别模型更换混在一轮里。CPU/GPU 或更高采样频率可作为之后的独立对照；当前最大风险是输入语义和控制权，不凭借推理加速推断可用性。

自动验证包括：

- 同一连续轨迹以 8/15/30 Hz 输入和 60/120 Hz 渲染回放，比较角度、速度与停下时间；建议先以最终转角差异不超过 5% 为调试目标，不将其当已达成绩。
- 80/200/600 ms 漏检、Worker 无返回、连续空帧、异常跳变、旧代次、时间倒退、重新入镜与换手；不存在位移补算、速度爆发或无限续转。
- 确认时指尖自然收拢、短遮挡、遮挡期间松开、候选消失、重叠热点和长停留；缺失不能自动完成进度或确认，持续悬停不重复执行。
- 鼠标接管、视角、聚焦、结构、导览、切换模式、校准、关闭、隐藏、离屏、上下文恢复与卸载之后无残留运动/时钟。
- 浏览器断言实际相机角度与动作次数，不能只检查提示文字。记录采样到结果、结果到画面更新的耗时；这些数值不等于摄像头到屏幕的完整物理延迟。

真人验收使用同一台桌面设备和摄像头，比较旧版与新版：向两边观察并停在指定角度、主动移出取景再回来、每种确认方式各 20 次选择、自然晃动但不选择。至少比较两种光照和左右手，记录成功/误触/取消/用时，以及“拖泥带水、意外滑动、能否停准”的评价。合成输入通过不能代替这一步；失败应先从诊断定位，不把所有情况统称识别率差。

实施后运行 `npm run check`、`npm run build`、现有浏览器/手势/交互/体验脚本，并保存桌面操作录像和结果表。本文仅为方案，当前没有这些新行为的测试成绩。

## 调研来源与采用边界

- [Map Gesture Controls](https://github.com/sanderdesnaijer/map-gesture-controls)：同属普通摄像头 + MediaPipe 的浏览器项目。README 描述动作持续确认、释放宽限、死区和平滑，可借鉴分层与参数化；本文不声称其已经实现这里设计的惯性。若复用代码，应先锁定提交并核验源码和许可。
- [Three.js Handtracking 101](https://github.com/collidingScopes/threejs-handtracking-101)：展示 Three.js/MediaPipe 控制球体的交互可行性，可参考反馈原型。它不是本项目商品选择、遮挡容错或真人可用性的证据。
- [One Euro 作者说明](https://gery.casiez.net/1euro/)：支持按速度平衡抖动与延迟，并说明低速、高速分开调参。继续使用现有实现，按项目坐标单位测量。
- [Ultraleap UI Components](https://docs.ultraleap.com/TouchFree/touchless-interfaces/ui-components.html)：借鉴软吸附、悬停、确认进度和动作反馈。其硬件与空间尺寸不能直接当作普通摄像头成绩或 CSS 像素规范。
- [Ultraleap Interactions](https://docs.ultraleap.com/TouchFree/touchless-interfaces/interactions.html)：Hover & Hold 适合选择，不能直接承担拖拽/滚动。由此建议把确认与连续运动分开，并把悬停作为本项目需要比较的候选默认方式。
- [Google Hand Landmarker Web](https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker/web_js)：保持关键点输入与 Worker 分离，采样和渲染各有时钟。更换封装库不等于解决交互层失踪与控制权问题。

结论和参数是针对本项目的设计推论，以上来源没有验证本项目的具体手感或成功率。
